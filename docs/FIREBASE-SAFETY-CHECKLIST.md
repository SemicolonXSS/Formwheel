# 🛡️ Formwheel Firebase 안전 점검 가이드

> 개발자용 체크리스트 · 작성일: 2026-11-08  
> 이 문서는 **진단 가이드**이며, 운영 Firebase 규칙이나 데이터는 변경하지 않습니다.

## 1. 변경 전 원칙

- [ ] 현재 운영 중인 Realtime Database Rules를 별도 파일로 백업한다.
- [ ] GitHub의 `database.rules.json`과 운영 규칙의 차이를 확인한다.
- [ ] 실제 방문자 수, 계정 프로필, Rapid 지갑·거래·인벤토리 데이터를 백업한다.
- [ ] 기존 경로를 삭제하거나 이름을 바꾸기 전에 모든 참조 코드를 조사한다.
- [ ] 공개 읽기와 인증 쓰기를 구분하고, 관리자 권한은 서버에서 검증한다.
- [ ] 검증 전에는 운영 배포하지 않는다.

## 2. 우선 점검 경로

| 영역 | 예시 경로 | 확인할 내용 |
| --- | --- | --- |
| 방문자 통계 | `formwheelV2/publicVisitorCounts` | 비로그인·로그인 조회 값 일치, 자동 Sync, 실시간 표시 |
| 세션 | `formwheelV2/liveHubSessions` | 세션 생성·갱신·10분 만료·권한 오류 |
| Rapid | `formwheelV2/rapidWallets` | 본인 접근, 잔액 일관성, 중복 거래 방지 |
| 테마 | `formwheelV2/themePreferences` | 본인 설정 저장·복원 |
| 프로필 | 실제 코드에서 경로 확인 | 로그인 유지, 공개 표시, 수정 권한 |

**주의:** 위 경로는 점검 후보입니다. 운영 DB의 실제 구조와 일치하는지 먼저 확인하세요.

## 3. Emulator 테스트 시나리오

- [ ] 비로그인 사용자는 공개 정보만 읽을 수 있다.
- [ ] 일반 사용자는 다른 사용자의 개인 데이터를 변경할 수 없다.
- [ ] 자신의 프로필·설정 저장이 정상 동작한다.
- [ ] Rapid 잔액 변경은 허용된 거래 흐름에서만 가능하다.
- [ ] 방문자 공개 집계가 로그인 여부에 따라 달라지지 않는다.
- [ ] 오래된 세션이 정리되더라도 현재 접속 세션은 유지된다.
- [ ] 잘못된 데이터 유형·음수·권한 없는 쓰기는 거부된다.
- [ ] 기존 저장 데이터와 이전 버전 클라이언트가 계속 동작한다.

## 4. 배포 판단

**GO:** 백업 확보 + Emulator 테스트 통과 + 기존 데이터 호환 확인 + 권한 검토 완료.

**NO-GO:** permission_denied 원인 미해결, 실제 운영 규칙과 GitHub 파일 불일치, 데이터 손실 가능성, 핵심 기능 회귀 발생.

## 5. 장애 시 복구

1. 새 규칙 배포를 중단한다.
2. 오류 시간·경로·로그인 상태·재현 절차를 기록한다. 토큰과 개인 정보는 기록하지 않는다.
3. 사전에 백업한 정상 규칙으로 롤백할지 검토한다.
4. 데이터 복원은 반드시 영향 범위를 확인한 후 별도로 수행한다.
5. 복구 후 비로그인 방문자·로그인·Rapid·세션 기능을 재검증한다.

---

운영 환경에 자동으로 적용되는 스크립트가 아닙니다. 실제 규칙 변경은 별도의 검토와 승인 후 진행하세요.
