# Formwheel 전체 비판적 분석 및 수정 — 2026-10-24

## 판단

프로젝트 종류가 많고 공유 모듈과 출시 검사가 이미 준비된 점은 강점이다. 현재 약점은 **프로젝트 분리·기능 변경 뒤 검색 주소, 테스트, 설명, 보상 조건이 함께 갱신되지 않는 것**이다. 신규 기능보다 기존 기능의 완료 경로와 데이터 신뢰성을 먼저 안정화할 필요가 있다.

점검 범위는 Hub 포함 GitHub 저장소 45개와 Hub 카탈로그 46개다. 각 저장소의 JavaScript 구문 및 HTML의 상대 정적 파일 참조를 검사하고, 존재하는 로컬 회귀 테스트를 실행했다. 모든 게임을 실제 플레이한 것은 아니며, 정적 파일 참조 검사는 동적으로 조립한 URL과 원격 URL의 배포 상태까지 확인하지 않는다. 저장소별 기준 커밋과 결과는 `audit-2026-10-24-source-checks.json`에 기록했다.

## 아직 남은 중요한 과제

1. **운영 보안 전환 확인:** 저장소의 Rules/서버 코드와 실제 운영 Firebase는 별개다. 현재 `firebase-security/README.md`도 클라이언트 전환과 운영 검증 미완료를 명시한다. 로컬 핵심 로직 통과만으로 점수·Rapid·멀티플레이가 서버 검증된다고 말할 수 없다. 이번 작업은 운영 Rules, 사용자 기록, 잔액을 변경하지 않았다.
2. **기능과 안내의 일치:** 예를 들어 Check는 개인 목록에서 초대 코드를 만들지만 다른 기기의 클라우드 공동 편집은 아직 연결되지 않았다고 안내한다. 완성도 비율보다 실제 가능한 흐름을 카드와 버튼에서 정확히 전달해야 한다.
3. **프로젝트 이동의 단일 관리:** 카탈로그는 assets/app.js, 사이트맵은 별도 XML, 이동 안내는 각 디렉터리에 분산된다. 신규 이동 때 카탈로그·사이트맵 검사를 필수로 실행해야 한다. 기존 자동 검사 자체는 유용했지만 실패가 남아 있었다.
4. **재방문 지표와 사람 수:** 프로젝트 열기는 실제 게임 완료와 다르고 UID/브라우저 기반 방문은 실제 사람 수와 같지 않다. 새 기능 수보다 시작→완료→재시작의 성공률과 이탈 지점을 측정해야 한다.
5. **실제 기기 확인:** 모바일 테마 가독성, 온라인 동시 참가·끊김·재접속, 게임 공정성은 소스·VM 테스트만으로 확정할 수 없다. 별도 실제 두 기기 테스트가 필요하다.

## 검증 한계

- 실제 브라우저 검증을 시도했으나 실행 파일이 없고 Chromium 다운로드가 손상된 응답으로 실패했다. 따라서 이번 결과를 브라우저·iPhone 실기기 검증 통과로 표시하지 않는다.
- 서비스 워커 테스트는 Node VM/가상 Cache API이며 실제 설치·업데이트 수명주기 전체 검증이 아니다. 온라인 방이나 계정에 테스트 데이터를 쓰지 않았다.
- Reflex 클라이언트의 정규화는 정상 코드 흐름의 일관성을 높인다. 변조된 클라이언트의 DB 직접 쓰기를 차단하는 서버 보안의 대체가 아니다.
- GitHub 반영과 Pages 운영 배포 완료는 구분한다. 운영 공개 화면 및 Firebase 호환성 전체를 검증했다는 뜻은 아니다.
